# FTCMS setup フェーズ最適化レポート

実施期間: 2026-07-14 〜 2026-07-15 ／ ブランチ: `sandbox`（コミット 31de0c16f 〜 773798726）

## 結論

フルラン（Mizo-xz-Convex, v2メッシュ 16,744節点/33,486要素, 24スレッド）で
**setup区間 9,679秒 → 1,329秒（-86%、全体比38.7% → 7.8%）、総実行時間 25,010秒 → 17,122秒（-32%）**。
全変更は回帰ケースで**bit-identical**（出力16ファイルのバイト一致・非線形反復回数一致）を検証済み。

## 背景と根本原因

プロファイラのsetup区間は初期化ではなく、**非線形反復ごとに呼ばれる後処理**
（節点相更新・保存量評価・T/P勾配投影・状態履歴管理）だった。特定した無駄は4系統:

1. **節点相更新の冗長評価** — `update_nodal_phases` が要素×局所節点ループで
   各節点を隣接要素数（約6回）重複して完全構成則評価（WRF・相変化・IAPWS密度・
   Darcy flux）。fluxは計算後に破棄。保存量評価 `compute_nodal_conserved` も
   同型の全節点評価を毎反復重複実行。
2. **stateの履歴配列ヒープ再割当** — `state%reset()` が履歴配列3本を
   deallocate し、直後の set が再allocate。`set_state` 呼出（数億回規模）ごとに
   最低3組の deallocate/allocate。assemble経路にも同じコストが乗っていた。
3. **T/P勾配投影の重複と幾何再計算** — L2投影が1反復に通常4回（初回6回）実行され、
   うち2回は入力不変の完全な冗長。毎回Gauss点ごとにヤコビアン・形状微分を再計算。
   すべて直列。
4. **直列実行** — 上記ループはいずれもOpenMP化されていなかった。

### 多材料境界の規約（今後の多材料計算向け）

節点Qw/Qi/Qa/Qvは残差・ヤコビアンにフィードバックしない（相更新が(T,p,φ)から
必ず上書きすることをコードフローで確認済み）。単一材料の節点（内部節点のほぼ全て）は
1回評価の直接格納で従来と完全一致。材料境界の節点のみ**材料ごとに評価→材料別
隣接測度で加重平均**（従来の「最後/最初の要素勝ち」というメッシュ順序依存の規約を、
決定的な規約に置換。単一材料メッシュでは挙動不変）。

## 検証方法

- 短縮回帰ケース: 平滑相と凍結開始相（dt崩壊・リトライ）の両方を含む22ステップ。
  2回実行でバイト一致（決定性）を確認した golden を基準に、各WP後に
  `regression/compare_outputs.py` で 16/16ファイルのバイト一致＋反復回数一致を要求。
- OpenMP化も加算順序を保存する設計（thread-local state・node-centric gather）で
  bit-identical を維持。
- 最終測定はクリーンビルド（build tree全消去→再ビルド）後にフルランで実施。

## フルラン測定結果（クリーンビルド・24スレッド）

| 区間 | ベースライン (7/13) | 最適化後 (7/15) | 変化 |
|:--|--:|--:|--:|
| setup | 9,679 s (38.7%) | 1,329 s (7.8%) | **-86%** |
| assemble | 9,324 s (37.3%) | 13,400 s (78.3%) | +44% ※ |
| solve | 1,581 s (6.3%) | 1,217 s (7.1%) | -23% |

※注意点:
- 24スレッド時は反復回数に実行間の非決定性がある（今回14,050回 vs 基準13,447回、+4.5%。
  2スレッド実行では基準と完全一致しており、コード変更起因ではなくMKL/OpenMP
  リダクションの既存挙動と判断）。
- assembleの1回あたり時間増（0.69→0.95秒）は当方の変更では説明できず、
  測定時の外部負荷またはベースラインバイナリのビルド条件差の可能性。
  ベースライン当時のバイナリは残っておらず確定不能。

## 運用上の知見

- `compile.py` は **Debug（-O0）固定**。性能運用にはReleaseビルドの導入を推奨。
- OpenMPI の `mpirun -n 1` はデフォルトで1コアにバインドする。性能実行は
  `--bind-to none` と `OMP_NUM_THREADS` の明示が必須。
- 回帰の再生成手順は `regression/README.md` を参照。

## 残課題

1. **assemble最適化**（現在78%で支配的）— setupで実証済みの手法
   （ヒープ削減・幾何キャッシュ・重複評価削減）が適用可能。調査着手済み。
2. Releaseビルドの測定と運用切替。
3. 二材料検証ケースの整備（多材料規約の受け入れテスト）。
